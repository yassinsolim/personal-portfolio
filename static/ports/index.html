Xbox 360 Call of Duty, recompiled for Android

How Call of Duty 4, Modern Warfare 2, Modern Warfare 3 and Advanced Warfare became native ARM64 Android apps, built on the player's own phone from the player's own disc.

These four games run on Android handhelds as native code. Nothing interprets PowerPC instructions while you play, and nothing is streamed. The console's machine code is translated ahead of time into C++, compiled for the phone's ARM64 CPU, and linked against a runtime that plays the part of the Xbox 360. On an AYN Thor all four hold 115 to 119 frames a second on its 120 Hz screen.

The unusual part is where that compile happens. The ports ship no game: no executables, no data, no generated code. The app reads your disc image, recompiles it on the phone in a few minutes, and keeps the result there.

None of this started from zero. XenonRecomp (hedge-dev) is the recompiler. mw2-recompiled, by Paul Combal and contributors, supplied the runtime these ports grew from. DrK's mw3recomp started the MW3 desktop work, the mw2-android fork supplied the first Android layer, and Xenia is the reference for how the console behaves.

Why recompile instead of emulate

An emulator has to be correct for every game. It translates code while the game runs and models the hardware in general, down to the 10 MB of EDRAM every frame is drawn into. A static recompiler translates once, ahead of time, with a full optimising compiler. The runtime then only has to be correct for one engine family, and that permits shortcuts. Modern Warfare 2 neither aliases its render surfaces nor draws in tiles, so EDRAM isn't emulated: each surface is a Vulkan image, and the few aliasing tricks the games do use are handled one at a time. The cost is that every game is a project of its own.

Step 1: PowerPC to C++

The Xbox 360's CPU is three big-endian PowerPC cores with two hardware threads each. A game ships as an encrypted, compressed XEX image. Once it's unpacked, XenonAnalyse finds the jump tables behind switch statements, and XenonRecomp writes every guest function out as a C++ function named after its address (sub_82459E58) that works on a struct of PowerPC registers. Loads and stores become byte-swapped accesses relative to one base pointer. Indirect calls go through a table indexed by guest address.

Most of the work is in each executable's configuration, which tells the recompiler what its analysis gets wrong. Advanced Warfare's campaign came out as 51,720 functions with 841 switch errors on the first run. They went to zero once the config stated 42 function extents and marked the exception-handler data that sits in front of some functions, which the recompiler had taken for code.

Some functions need more than a correct translation. The engine recovers from errors by longjmp-ing back to its frame loop. Translated literally, that jump returns into the code that raised the error, and a multiplayer client dropped at the end of a match hung there. So the config names the pair and the recompiler emits real host setjmp/longjmp in their place. Every recompiled function is also a weak symbol, so the runtime can replace any one of them with its own, which is how it hooks Direct3D's present and the engine's error and print paths.

Step 2: standing in for the console

The games talk to the console through two system modules, xboxkrnl.exe and xam.xex. Direct3D, XAudio2 and the network libraries are linked into the game, so they're recompiled with it. Each import becomes a function the runtime provides. Any import it doesn't provide gets a generated stub that logs its name once and returns zero, so a run reports exactly which missing pieces it reached. When Advanced Warfare first recompiled, the runtime already had 227 of the 288 imports it asked for.

Memory. The recompiled code addresses memory as a 32-bit offset from one host pointer, so the whole 4 GiB guest space is one reservation and a guest pointer costs one addition. Direct3D reads the console's 512 MB of RAM through two address windows, so one shared memory object is mapped at both 0xA0000000 and 0xC0000000.

Threads. Each guest thread is a host thread with its own guest stack and a processor block behind register r13, which the code reads about 1,100 times. The details matter. The engine's render lock compares thread IDs, so with every thread reporting 0 it deadlocks. The renderer's jobs only run on hardware threads 1 and 2, so a thread's processor number has to be the one it asked for.

Small lies cost a lot. Call of Duty 4 kept failing with "out of memory" on its larger levels. Its memory pool asks the kernel how a page is protected and starts a fresh 64 KB page when the answer isn't what it wants. The runtime always answered "read-write", so every write-combined allocation took a page of its own, and one level came out 3 MB short of its 431 MB pool. The fix was to remember the protection that was set.

Step 3: the GPU, from PM4 to Vulkan

Direct3D 9 is linked into the game with whole-program optimisation and no symbols, so there's no API boundary to intercept. Instead the runtime plays the GPU's command processor. Direct3D writes PM4 packets into a ring buffer, and a runtime thread follows its write pointer and executes them: register writes go into one register file, shader loads go to the translator, and draws go to the renderer. A draw packet carries only the primitive and indices. Everything else is whatever the registers hold at that moment.

Xenos quirks have to be copied exactly. It expresses "+Y is up" as a negative viewport scale, so dropping the sign flips the frame and every triangle's winding. Direct3D clears a colour surface by treating it as a depth buffer and stamping stencil values into it, so the runtime recognises that pattern and performs a real clear.

The ring consumer copies each frame's indices, constants and vertices into one arena. A recorder thread makes the Vulkan calls and a window thread presents. Going past 60 frames a second meant lifting two caps. One is Direct3D's present interval. The other is the engine's own limiter, which counts whole milliseconds and so would let 125 frames through while a 120 Hz panel shows 120. When the limit matches the display, the limiter is switched off and the swap waits for the window instead.

Shader translation

The games compile no shaders at run time. They load Xenos microcode, already compiled by Microsoft's offline compiler, through the command stream. The runtime hashes each program once, caches it until its memory is written, and translates it straight to SPIR-V.

Xenos control flow can jump, call and loop anywhere. A program that does any of that becomes one loop around a switch on the program counter. A program that doesn't, which covers nine in ten pixel shaders and every vertex shader, is emitted as straight-line code. That matters because drivers don't untangle the loop themselves and keep every register live across it. Predicated instructions become selects, since on Xenos they still run and only their writes are suppressed.

Vertex shaders only get their vertex formats once the game binds them, when Direct3D patches them in place, so the runtime takes them after binding. With VK_EXT_graphics_pipeline_library, worker threads compile shaders while a level loads, draws link the prebuilt pieces, and an idle thread relinks them with link-time optimisation. Every translation is checked with spirv-val and with a real driver compile, because drivers happily accept invalid SPIR-V.

Building the game on your phone

The recompiled code is the game, so it can never be shipped. The repositories hold the runtime, the app and the recompiler setup, and a pre-commit check refuses anything that looks like game data. Every player builds from their own disc, and the result stays on their own device.

That used to take a PC. Now a second app, com.recomp.toolchain, carries the build tools: one 43 MB package with no code, screen or permissions, shared by all four games. Inside are clang and lld 19.1.7 cross-built from LLVM's sources as a single program (90 MB unpacked, against 140 MB as two), XenonRecomp, and a sysroot built from AOSP's bionic headers.

Android has to be worked with, not around. Since Android 10 an app can't execute files it wrote. It can run programs from a package's native-library folder, but only files named lib*.so are unpacked there. So the compiler ships as libllvm.so, and the game's app asks the package manager where that folder is. An app may not run a program it wrote, but it may load a library it wrote, so the freshly linked game is opened with dlopen and nothing is packaged or signed on the device.

The executables are accepted only if their SHA-256 matches a supported build. Before compiling, the build compares a statement of what the recompiler produced with the one the app expects. A mismatch stops it within half a minute, and a finished library matches the PC build's statement byte for byte. The build runs as a foreground service, because background apps get only the three small cores on the Thor. It runs fewer compilers when memory is short or the battery passes 46 °C, and it resumes where it stopped after an interruption.

Graphics drivers

On the Thor's stock Qualcomm driver a single pipeline took up to half a second to compile. A level's first minutes showed see-through walls, Modern Warfare 2 ran at 36 to 49 frames a second, compressed textures flickered black, and some scenes broke up into grids of square blocks. So the apps ship Turnip, Mesa's open-source Vulkan driver for Adreno, loaded through libadrenotools, and use it by default on Qualcomm chips. Turnip had problems of its own: on the Flip 2's Adreno 650, its image compression hard-reset the whole device within a second of every level start. With compression off, there have been none in eighteen starts since, at the same frame time.

Turnip builds vary, and players bring their own, so the app now proves a driver before using it. A catalog lists packages per chip, each pinned by SHA-256. The best candidate is self-tested in a separate process, so a crash takes down the test and not the app. The test creates the Vulkan device exactly as the game does, draws one 64×64 frame with shaders built the way the renderer builds them, reads it back and checks the pixels. Then the game's first frames are sampled until they look like a picture, using rules tuned on 19,006 samples from 102 recordings. If they don't, the app asks the player instead of switching drivers silently.

The test had a bug of its own. Its first version rejected three community Turnip builds that crashed compiling its vertex shader, a shader the games never use. Once the shader was fixed, all three passed and ran Modern Warfare 3's Survival at 117.9 to 118.8 frames a second.

Performance on the AYN Thor

These numbers come from the visual-QA suite, the release gate. Each scenario installs a fresh copy of the app (cold caches, like a new player's), plays a level or match from a gamepad script, and records the screen. Every recorded frame is checked for flicker, block artifacts, missing geometry, black or frozen frames and stalls, and the game's log gives the frame rate. This is one suite run from 27 November 2026 on the bundled Turnip, in which all twenty runs passed.

What didn't work

  • Frame generation. I built an interpolator that searched for motion between two frames. Its in-between frames scored 31.0 dB PSNR against the frames the game really drew, but each frame reached the screen 17 to 18 ms later. The HUD smeared too, since it's drawn into the same image as the world, and the games already render 115 to 118 real frames on the Thor. Not kept.
  • Upscalers. Temporal ones (FSR 2/3, Snapdragon GSR 2) need motion vectors and a jittered projection taken from four games' executables, so they weren't built. Spatial ones did no better than plain RCAS sharpening. Snapdragon GSR 1 cost as much and scored lower, and FSR 1's EASU cost two to two and a half times as much for the same quality.
  • Variable-rate shading. Not built. On the Thor, a scene with two thirds of the pixels ran no faster (106.2 against 107.1 frames a second), so saving pixels doesn't help there.
  • More threads. A second thread for vertex copies made Flip 2 frames slower (14 to 18 ms), because the consumer ended up waiting on a slow, cold core.
  • Skipping draws while pipelines compile. The old Android approach, and the cause of the see-through walls. Turnip and compiling while a level loads made it rare, but a fresh install can still lose a few draws for one frame when more pipelines are new at once than there are workers.
  • Still open. Mali GPUs are untested on a real phone. Advanced Warfare with sun shadows on has a shadow flicker whose cause isn't known yet.

Try it

You need your own disc image, an Android 10+ device with a Snapdragon 865 or newer (8 GB of RAM recommended), and a few minutes for the build. The AYN Thor and Retroid Pocket Flip 2 are the tested devices. Each repository has the APK, the setup steps and the full technical docs this post summarises.
